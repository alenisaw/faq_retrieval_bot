# Тестовый набор: правила разметки

Набор нужен для протокола A: на нём считаются финальные метрики, подбирается порог
отказа и выбирается метод для бота. Запросов из самого FAQ в наборе быть не должно,
иначе любой метод даст P@1 ≈ 1 (утечка).

## Файлы

`test_queries.csv`: `query_id, text, author, split, is_oos, origin`
- `split`: `unassigned` до заморозки, потом `dev` (30%) или `test` (70%);
- `is_oos`: 1 — вопрос не по теме (бот должен отказать);
- `origin`: `manual` или `llm_draft` (черновик LLM, проверенный человеком).

`qrels.csv`: `query_id, answer_cluster, topic` — gold-ответы; у запроса не по теме строк нет.

Файлы не правятся руками: всё добавляется через `python -m src.annotate`, он проверяет
кластеры, темы, дубли и совпадения с вопросами FAQ.

## Как писать запросы

Каждый пишет ~60 запросов по теме и ~10 не по теме.

- Пишите так, как пишет абитуриент в чате: «общага есть?», «скок стоит учеба»,
  «проходной на се», с опечатками, сокращениями, транслитом, без заглавных и знаков.
- Не копируйте и не перефразируйте слово в слово вопросы FAQ. Сначала придумайте
  вопрос, потом ищите ответ.
- Покройте все 12 тем (`config.TOPICS`), примерно по 5 запросов на тему.
- Разная длина: от одного-двух слов до длинного вопроса с контекстом.
- Не по теме — то, о чём абитуриент мог бы спросить бота, но что к AITU не относится:
  погода, другие вузы, бытовые вопросы.
- Вопросы про AITU, ответа на которые в FAQ нет, в эту версию набора не включаем:
  их нельзя честно отнести ни к «есть ответ», ни к «не по теме».

## Разметка gold-ответа

- Релевантен кластер, ответ которого полностью отвечает на вопрос.
- Если подходят несколько кластеров (например, два почти одинаковых ответа про стоимость),
  отметьте все через запятую.
- Если среди кандидатов нужного ответа нет, ищите по подстроке: `f общежит`.
- Тема по умолчанию — тема выбранного кластера; меняйте, только если она явно не подходит.
- Не подбирайте запросы под то, что находит какой-то метод.

```bash
cd backend
python -m src.annotate --author ayan        # интерактивная разметка своих запросов
python -m src.annotate --check              # статистика: авторы, темы, доля LLM
```

## Черновики LLM

Допускаются, если каждую строку проверил человек; доля в итоговом наборе — не больше 50%,
это указывается в отчёте. Черновик — CSV в `eval/drafts/` с колонками
`text, author, is_oos, answer_cluster, topic, origin, reviewed`: после проверки строки
ставится `reviewed=1`, непроверенные строки при импорте пропускаются.

```bash
python -m src.annotate --import eval/drafts/ayan_llm_draft.csv
```

Чтобы проверять черновик в Excel, сначала переведите его в формат для Excel, иначе вместо
русского текста будут кракозябры и всё окажется в одной колонке (Excel с русской локалью
ждёт cp1251 и «;»):

```bash
python -m src.annotate --excel eval/drafts/ayan_llm_draft.csv
```

После правок сохраняйте как «CSV UTF-8» или обычный «CSV» — импорт понимает оба варианта.

## Перекрёстная проверка и Cohen's kappa

Каждый независимо, не глядя в чужую разметку, размечает запросы одного из коллег:

```bash
python -m src.annotate --author ayan --review alen     # Аян размечает запросы Алена
python -m src.annotate --agreement eval/reviews/qrels_review_ayan_on_alen.csv
```

Kappa по теме и по кластеру идёт в отчёт до исправлений. Расхождения обсуждаются втроём
и исправляются в `qrels.csv`.

## Заморозка

Когда все запросы добавлены и проверены — один раз:

```bash
python -m src.annotate --freeze      # dev 30% / test 70% со стратификацией по темам
python -m src.experiments --protocol test
```

После заморозки набор не меняется. Порог и веса гибрида подбираются только на `dev`,
финальные цифры — только на `test`.
